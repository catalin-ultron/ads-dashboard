### MPXJ in-memory calendar (`mpxj/src/main/java/org/mpxj/ProjectCalendar.java`)

- Identity: uniqueID, GUID, name, `type` (`CalendarType` GLOBAL/PROJECT/RESOURCE), `projectUniqueID`, `personal`, `parent` (ProjectCalendar), default flag.

## Algorithms and logic

### A1. Working-hours resolution for a date (`ProjectCalendar.getRanges`, ProjectCalendar.java:1851-1891)

1. Exception for the date in this calendar (binary search over sorted, recurrence-expanded exceptions), else in the parent chain (`getException`, 1288-1336) → its ranges (empty = non-working).
2. Else the work week covering the date in this calendar, else parent's (`getWorkWeek`, 1344-1390); else the base week.
3. Day type of that week: NON_WORKING → empty; WORKING → its hours; DEFAULT → parent's hours for the weekday (empty if no parent).
`getDayType` for a root calendar treats DEFAULT as Sat/Sun non-working, other days working (1070-1085). `isWorkingDate` = ranges non-empty (1105-1108).

P6 import specifics: a weekday record with no hours is set non-working; otherwise working iff it has ranges (TableContextReader.java:707-727). Each exception is a single date (`d` epoch days) with optional hours; no hours means non-working (TableContextReader.java:772-800). `ensureWorkingTime` guarantees at least some working time (`ProjectCalendarHelper.ensureWorkingTime`).

### A2. Date + duration (`ProjectCalendar.getDate`, ProjectCalendar.java:643-927)

- Elapsed units: add elapsed minutes directly.
- Positive: convert to milliseconds via the calendar's minutes-per-period; walk day by day: if the remaining work equals the day's work from the current time, finish at that day's finish time; if larger, subtract and jump to the next working date at its start time (guard: give up after 1000 consecutive non-working days, `MAX_NONWORKING_DAYS`, 2142); if smaller, walk the day's ranges from the current time and end inside a range. Result truncated to seconds; last call memoised for incremental reuse (666-680).
- Negative: mirror image walking backwards through ranges in reverse, ending at a range start.
- P6 engine wrapper rounds to the nearest minute (`mpxj/src/main/java/org/mpxj/cpm/PrimaveraDateCalculator.java:112-128`).

### A3. Boundary helpers and work-between (ProjectCalendar.java)

- `getNextWorkStart(d)` (936-997): if d lies before the end of a range today, return max(d, range start); else first working day's start time.
- `getPreviousWorkFinish(d)` (1006-1057): latest range end ≤ d today, else previous working day's finish.
- `getWork(start, end, unit)` (1430-1543): elapsed formats use wall-clock minutes; otherwise sums working time of partial first day, full intermediate days and partial last day; inverted ranges return negative.
- P6 engine "equivalent" helpers only move a date across a boundary if no working time lies between (`PrimaveraScheduler.java:4112-4167`); 24-hour lag calendar is a synthetic all-days 00:00-24:00 calendar (`PrimaveraDateCalculator.java:142-152`).

### A4. Time-unit conversion (ProjectCalendar.java:128-231; `mpxj/src/main/java/org/mpxj/TimeUnitDefaults.java`)

Minutes per day/week/month/year = calendar's own value, else parent's, else project `TimeUnitDefaults`; days per month always from project defaults. P6 import (TableContextReader.java:613-672): uses `day_hr_cnt` etc.; if any is missing derives minutes/week = Σ range minutes over the base week, minutes/day = minutes/week ÷ working days, month = 4 weeks, year = 12 months (P6 itself does not validate these values). P6 durations and lags are stored in hours (`*_hr_cnt`) and converted with `Duration.convertUnits(target, calendarOrProjectProperties)`. The P6 scheduler converts lag to hours with project properties (not the activity calendar) whenever it compares lag to actuals.

### A5. LibrePlan capacity lookup (`libreplan/libreplan-business/src/main/java/org/libreplan/business/calendars/entities/BaseCalendar.java`)

`findCapacityAt(date)` (292-303): not active (outside every `CalendarAvailability`, when any exist) → zero; own exception, else parent's exception not shadowed by an own exception on the same date (`getExceptions(date)`, 206-219) → exception capacity; else `getCapacityConsideringCalendarDataOn` (309-320): version = first `CalendarData` whose expiringDate is null or after the date (625-637); weekday capacity, null → parent (version-specific parent) → default zero with unlimited overtime. `getCapacityWithOvertime` multiplies by calendar units (`ResourceCalendar.capacity`, e.g., a virtual worker of 10) (286-290, `ResourceCalendar.java`). `asDurationOn(day, resourcesPerDay)` = min(capacity limit, resourcesPerDay × day standard effort) rounded to the nearest minute (963-975). Workable days for a task = days with non-zero capacity on the task calendar (`planner/entities/Task.java:1100-1132`).

### A6. Odoo work intervals (`odoo/addons/resource/models/resource_calendar.py`)

- Attendance intervals (287-454): computed per resource timezone; for each date, attendances matching the date's weekday (or explicit date/recurrence) become [day + hour_from, day + hour_to] in the resource tz, converted to UTC; duration-based attendances are centred on 12:00.
- Work intervals = attendance − leaves (global + resource leaves of `count_as=absence`) (525-542).
- `plan_hours(hours, dt)` (764-808): iterate 14-day windows up to 100 times, consuming interval hours until the remainder fits; negative hours walk backwards. `plan_days(days, dt)` (810-852): count distinct dates with intervals until `days` reached, return that interval's stop (or start when negative).
- `get_work_hours_count` / `get_work_duration_data` (699-762) sum interval lengths between datetimes.

### A7. TaskJuggler slot scoreboards (`taskjuggler/lib/taskjuggler/Project.rb:1269-1301`, `taskjuggler/lib/taskjuggler/ResourceScenario.rb:830-905`)

Project horizon split into `scheduleGranularity` slots. Global scoreboard: each slot starts as 2 (off-hours); slots on shift per `workinghours` become nil (working); global leaves set bit 2+ type `(… | (1 << 2))`. Resource scoreboard: same, then resource leaves stored as `typeIdx << 2` preserving work-time bit `0x2`, higher leave type wins; shift assignments merged: if bit 8 (replace) set, the shift's slot value replaces global leaves, else shift leaves with higher type are merged. A slot holding a `Task` object is booked. `isWorkingTime` = slot nil (Project.rb:880-900). `gapLength` lags count working slots on the global scoreboard.

### A8. IFC day-level calendar (`ifcopenshell/src/ifcopenshell-python/ifcopenshell/util/sequence.py:96-270`)

`is_working_day(day, cal)`: some WorkingTime applies to the day (date inside Start/Finish window and recurrence matches) and no ExceptionTime applies. Recurrence matching implemented only for patterns without Interval/Occurrences (weekday lists, day-of-month, monthly/yearly by position); other cases return False (TODO). `is_calendar_applicable` false outside every WorkingTime window, in which case days count as working. `offset_date`, `count_working_days`, `get_start_or_finish_date` work in whole days with 09:00 start / 17:00 finish stamps (see D06 A13).

### A9. OpenProject working days (`openproject/app/services/work_packages/shared/working_days.rb`)

`working?(d)` = weekday in `Setting.working_days` and date not in `non_working_days` (raises if no working weekdays). `duration(start, due)` = count of working dates inclusive; `due_date(start, n)` / `start_date(due, n)` step over working days; `with_lag(date, lag)` starts the day after and counts `lag` working days (negative lag counts back).

### A10. Resource availability in the P6 model

Max units per time are effective-dated: rows sorted by `start_date` per shift period; each row's end = next row's start − 1 minute, open-ended rows end at `END_DATE_NA` (TableContextReader.java:943-986). `ShiftPeriod.getDuration()` = next period start − this start (wraps at 24h) (`ShiftPeriod.java:80-90`). No function multiplies calendar hours by max units; capacity per period must be computed by the consumer (D08). The P6 scheduler ignores max units.

### A11. Time zones

- MPXJ: all P6 dates are `LocalDateTime` without zone; no time-zone fields are read.
- Odoo: intervals computed in `resource.tz` (or company tz in `plan_days`), stored in UTC; leaves stored UTC (resource_calendar.py:287-306, 764-775).
- TaskJuggler: `WorkingHours.timezone` applied when building the scoreboard (`WorkingHours.rb`).

### A12. Store period performance

No source implements snapshotting actuals into financial periods; ERPNext Accounting Period only blocks posting of listed document types inside closed periods.

## State machines and workflows

- LibrePlan calendar versioning: a calendar is an ordered list of `CalendarData` versions with expiring dates; `newVersion(date)` splits the current version; the last version has null expiry and must exist ("Some work week should not be expired") (BaseCalendar.java:399-560, 625-637). Each version can have a different parent, so inheritance itself is time-dependent.
- LibrePlan `CalendarAvailability` windows must not overlap (BaseCalendar.java:945-960); a new `ResourceCalendar` starts with an availability from today with no end.
- Odoo `calendar_type` transitions (fixed/variable/undefined) drop incompatible attendances (`_get_attendances_to_unlink`, resource_calendar.py:105-116).

## Cross-domain links

- D03/D06: activity calendar (`TASK.clndr_id`) governs every duration and float computation; lag calendar option picks predecessor/successor/project-default/24h calendars.
- D04: lag arithmetic on lag calendars; OpenProject lag counts working days.
- D07/D08: resource calendars, shifts and max units drive Resource Dependent scheduling and leveling; LibrePlan `ResourceCalendar.capacity`.

## Gaps

- Resource availability per period (calendar working hours × effective-dated max units per shift period) must be implemented.
- Store Period Performance (snapshot of to-date actual units/costs per financial period per activity/assignment, editable past-period actuals) has entities only (PMXML) and no logic.
- Project/user time zones for P6-style data: add zone ids on project and user and normalise to UTC; date-only fields must be kept distinct from datetimes.
- Calendar-specific vs admin "hours per time period" toggle: MPXJ always prefers calendar values with fallback; the user-selectable switch must be added.
- IFC recurrence with Interval/Occurrences is unimplemented; IFC and OpenProject are day-granular only.
